# Hectra for editors — комплект фронтенда для переделки

Эта директория — отдельная копия фронтенда локального прототипа **Hectra for editors**, подготовленная для передачи команде, которая будет перерабатывать интерфейс. Исходные файлы проекта остались на своих местах. Комплект отражает состояние файлов на момент копирования 23 сентября 2026 года; вложенная техническая документация описывает продукт по состоянию на 19 августа 2026 года.

## Как устроен интерфейс

Фронтенд написан на обычных HTML, CSS и JavaScript без сборщика и UI-фреймворка. Порядок `<script>` в `workspace.html` существенен: сначала загружаются конфигурация, чистые движки и state, затем renderer и UI-модули, в конце `app.js`. При переносе в новую архитектуру нужно сохранить зависимости и поведение, даже если способ организации файлов изменится.

Главный объект продукта — **живой Markdown-документ из адресуемых секций**, а не только лента сообщений. У секции есть стабильный ID; текущий порядок хранится отдельно. Ответ модели использует текстовый протокол вида `## Заголовок [#id]`, а перемещение и удаление оформляются маркерами `@before`, `@after`, `@start`, `@end` и `DELETE`. Парсер, edit engine и state совместно проверяют эти операции.

Ключевые сценарии для переделки UI:

1. Создание документа и обычный диалог через composer.
2. Изменение одной/нескольких секций или всего документа. Запрос фиксирует исходный снимок и разрешённые ID до обращения к модели.
3. Review предложенных изменений: допустимые правки выбранных секций могут применяться автоматически; изменения вне области и структурные операции требуют явного включения, некорректные операции не применяются. Финальное применение выбранного набора атомарно.
4. Ручное изменение порядка/состава секций в отдельном черновике с одним финальным применением.
5. Альтернативные ветки документа, Map, временный вопрос по снимку ветки, версии и слияние.

Канонические данные документа и веток находятся в `HectraState`; UI-модули должны хранить только состояние отображения. `editEngine.js`, `mergeEngine.js` и `structureAssistant.js` рассчитаны на работу без DOM, сети и браузерного хранилища. Подробные инварианты и сценарии описаны в техническом документе и UX-аудите.

## Локальный просмотр и проверки

Для просмотра страниц можно запустить любой статический HTTP-сервер из этой директории. Например, при установленном Python:

```powershell
cd frontend_handoff
python -m http.server 8000 --bind 127.0.0.1
```

Затем открыть `http://127.0.0.1:8000/` или `http://127.0.0.1:8000/workspace.html`. Это позволит оценить статический интерфейс; обращения к модели требуют отдельного API-сервера.

Для тестов нужен Node.js (исходная документация фиксировала проверку на версии 20.19.0):

```powershell
cd frontend_handoff
npm test
```

Тесты используют встроенный `node:test`; `npm install` и `node_modules` для них не требуются. `diagnostics/browser-qa.js` сохранён как справочный сценарий проверки браузерных потоков, но не является автономной командой данного пакета.

## Подключение API и важные границы

В `js/app.js` предусмотрены два режима: `direct` (браузер вызывает провайдера) и `proxy` (браузер вызывает `POST http://127.0.0.1:3000/api/chat`). Выбор находится в Settings и сохраняется в `sessionStorage` под ключом `hectra_api_mode`; исторический режим по умолчанию — `direct`. В этой копии `HectraConfig.API_KEY` намеренно пустой, поэтому direct-запросы не заработают до отдельной настройки. Не помещайте реальный ключ в клиентский код. Для действующего приложения подключайте безопасный серверный proxy и храните ключ только на стороне сервера.

Этот комплект **не содержит** `server.js`, `.env`, `.env.example`, исходные зависимости/lockfile, `node_modules`, материалы `films/`, массовые скриншоты, логи и профили браузера из `diagnostics/`. Серверная реализация и её ограничения описаны в техническом документе; API-адрес в `config.js` нужно согласовать со средой будущего фронтенда. Внешние ресурсы текущих страниц: CDN для Tailwind, Marked, KaTeX и PDF.js, а также Google Fonts. Работа без сети может изменить внешний вид и часть рендеринга.

Текущий прототип хранит данные преимущественно в `sessionStorage`; постоянная серверная база, учётные записи и синхронизация между устройствами не реализованы. Документация также отмечает ограничения Undo, временного чата, merge-контекста и старые риски безопасности. При редизайне полезно сверять UX-решения с фактическими контрактами `state.js`, движков и тестов, а не только со старым снимком экрана.
